이력서/포트폴리오 PDF를 수정하거나 만들 때 따라야 할 규칙입니다.

## 이력서/포트폴리오 PDF 수정 및 생성

### 대상 문서

- `MissionSystem` 저장소 루트의 포트폴리오_Unreal_박인호.pdf
- 비공개 저장소 `https://github.com/inhopark/Resume`의 자기소개서_박인호.pdf, 경력기술서_박인호.pdf
  - 공개 저장소에서 개인 문서를 숨기려고 2026-09-23에 이동했다.
  - 자기소개서/경력기술서는 공개 저장소(`MissionSystem`)에 다시 커밋하지 않고 `Resume` 저장소에서 작업한다.

이 문서들은 원본 문서 파일이 아니라 **HTML을 헤드리스 Chrome/Edge로 인쇄해 만든 PDF**다. grep -a -o "Producer\\|Creator" 자기소개서_박인호.pdf로 확인하면 `Producer (Skia/PDF m153)` / `Creator (Mozilla/5.0 ...)`가 나온다. 즉 python-docx/pandoc 등이 아니라 브라우저 인쇄 파이프라인의 산출물이다.

### 작업 절차

이 중 하나를 수정해 달라는 요청을 받으면 항상 다음 절차를 따른다.

1. **원본과 같은 톤으로 HTML 레플리카를 작성한다.**
   - 어두운 타이틀 텍스트
   - 초록색(`#16794f` 계열) 포인트 컬러
   - 초록 사각형 안에 숫자가 들어간 섹션 배지(`1`, `2`, …)
   - 옅은 초록 배경의 정보 카드(프로젝트 유형 / 클라이언트 / 서버 / `DB` 등)
   - 초록 필(pill) 형태의 소제목 태그
   - `▸` 불릿 목록
2. **로컬 헤드리스 브라우저로 그 HTML을 PDF로 렌더링한다.**

```
"C:\Program Files\Google\Chrome\Application\chrome.exe" --headless=new --disable-gpu --no-pdf-header-footer --print-to-pdf="<출력 경로>.pdf" "file:///<html 절대경로, 슬래시 표기>"
```

   - 경로는 `file:///C:/...` 형태(트리플 슬래시 + 슬래시 구분)여야 한다.
   - Git Bash 스타일 `/c/...` 경로를 그대로 넘기면 네이티브 Windows Chrome이 인식하지 못해 `ERR_FILE_NOT_FOUND`가 난다.
3. **원본을 덮어쓰지 않는다.** 결과물은 같은 폴더에 `_draft` 접미사를 붙인 새 파일로 저장한다(예: 자기소개서_박인호_draft.pdf). 사용자가 내용을 확인한 뒤 원본 교체 여부를 직접 결정한다.
4. **`_draft` 파일은 사용자가 명시적으로 요청하기 전까지 git에 add/commit하지 않는다.**
5. **페이지 나눔(break) CSS는 최소한으로만 건다.** 페이지 중간에 큰 빈 공간이 남지 않게 하기 위해서다.
   - `.company-block` / `.project`처럼 페이지 하나보다 커질 수 있는 큰 컨테이너에는 `page-break-inside: avoid`(또는 `break-inside: avoid`)를 걸지 않는다. 블록이 남은 공간에 들어가지 않으면 통째로 다음 페이지로 밀려나서 이전 페이지에 큰 여백이 생긴다. 실제로 이 문제로 자기소개서_박인호.pdf가 6쪽, 경력기술서_박인호.pdf가 3쪽까지 늘어났던 전례가 있다(각각 4쪽 / 2쪽으로 정정됨).
   - 소제목이 페이지 맨 아래에 혼자 남는 것만 막는다. 제목류(`.tag`, `.project-title`, `.sub-title`, `.company-row`, `h3` 등)에는 `break-after: avoid`를 건다.
   - `break-inside: avoid`는 불릿 한 줄이나 정보 카드처럼 원래 작은 단위(`ul.bullets li`, `.info-card`)에만 건다. 본문은 페이지 경계를 넘어 자연스럽게 이어지게 한다.
6. **폰트 크기/굵기는 경력기술서_박인호.pdf(2026-09 개정판) 기준을 그대로 맞춘다.** 사용자가 이 크기감을 명시적으로 마음에 들어해 표준으로 삼기로 했다.

| 요소 | 크기 / 굵기 |
|---|---|
| 본문 텍스트 | 10pt, `line-height: 1.55` |
| 문서 타이틀(`h1`, 예: "경력기술서") | 22pt, `font-weight: 800` |
| 섹션 제목(`h2`, 번호 배지 옆) | 13pt |
| 섹션 배지(`.badge`) 숫자 | 10pt, `font-weight: 700` |
| 프로젝트명(`.proj-title`, 예: "The Patcher") | 10.5pt, `font-weight: 700` |
| 스튜디오·기간(`.proj-meta`) | 8.5pt, 연회색 |
| 소제목 초록 필 태그(`.subtag`, 예: "핵심 게임 시스템 개발") | 8.3pt, `font-weight: 700` |
| 역량/성과 옆의 작은 초록 필 태그(`.tag`, 예: "Unreal", "The Patcher") | 7.8pt, `font-weight: 600` |
| 세부 불릿(`ul.bullets li`) | 9pt |

   - 이 기준에서 벗어나게 바꾸려면(더 크게/작게) 반드시 사용자에게 먼저 확인한다.
7. **사용자가 "이 섹션은 몇 쪽부터 시작"처럼 특정 섹션의 시작 페이지를 지정하면** 다음과 같이 한다.
   - 5번의 "큰 컨테이너에 `break-inside: avoid` 금지" 원칙은 그대로 지킨다.
   - 해당 섹션/하위 제목 요소에만 `.page-start { break-before: page; }` 클래스를 추가해 강제로 새 페이지를 시작시킨다. 자동 리플로우에 맡기지 않는다.
   - 여러 지점에 걸 수 있다(예: 3번 섹션 제목, 4번 섹션 제목, 4번 안의 C# 소제목, 5번 섹션 제목에 각각 적용).
   - 목차(TOC)의 `p.N` 표기가 실제 렌더링 결과와 일치하는지 반드시 다시 렌더링해서 확인하고, 필요하면 TOC도 함께 고친다.
   - 특정 구간의 분량이 지정한 페이지 안에 물리적으로 들어가지 않으면(margin/line-height를 줄여도 안 맞으면) 임의로 더 줄이지 않는다. 사용자에게 옵션(페이지 늘리기 / 섹션 더 쪼개기 / 해당 구간만 폰트 축소 / 내용 자체를 축약)을 제시해 확인받는다.
   - 폰트 축소가 선택되면 6번 표준 크기를 문서 전체가 아니라 **그 구간에만** 범위를 좁힌 클래스(예: `.proj-block.compact`)로 적용한다. 6번 표준 자체는 건드리지 않는다.
8. **CSS/내용을 바꿨는데 다시 렌더링한 PDF 결과가 전혀 바뀌지 않으면 Chrome의 로컬 디스크 캐시를 의심한다.**
   - 헤드리스 Chrome이 `file://` 리소스를 이전 `--print-to-pdf` 실행 결과로 캐싱해 최신 수정사항을 반영하지 않은 사례가 실제로 있었다.
   - 이럴 땐 매번 새 프로필로 강제 렌더링해서 다시 확인한다. 렌더링 명령에 --user-data-dir="<매번 다른 임시 경로>" --disk-cache-dir="<매번 다른 임시 경로>"를 추가한다(경로 끝에 매번 바뀌는 난수 값을 붙임 — Bash는 `$RANDOM`, PowerShell은 `Get-Random`).
   - 렌더링이 끝나면 이 임시 프로필/캐시 디렉터리는 정리한다.
